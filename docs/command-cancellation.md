# Command cancellation

Status: command cancellation is connected through the authenticated API, durable PostgreSQL operations, controller and supervisor to the existing guest runner. Cancellation of create, destroy, cancellation operations and file mutations is unsupported. This document owns the implemented cancellation flow; [API contract](api-contract.md) owns shared authentication and idempotency semantics.

## Request and result

Send `POST /v1/operations/{execute_operation_id}/cancel` with a current project bearer token, a new `Idempotency-Key`, and the JSON object `{}`. Unknown body fields are rejected. The response is `202` with a separate cancellation operation ID and status URL. Poll that operation; its `target_operation_id` identifies the original command. The same field appears in operation lists.

An identical retry returns the original cancellation handle, including after the command finishes or its sandbox is destroyed. A changed target under the same key returns `409 conflict`. Expired cancellation-response retention returns `410 response_expired` with the original cancellation ID; payload compaction preserves this identity. Missing and cross-project targets both return `404`. Unsupported target kinds return `409`. Only one unfinished cancellation request is admitted per target; another key receives `409 command_in_progress` with the existing cancellation ID and consumes no key.

A cancellation operation succeeds once its target has a confirmed terminal status. Its result contains `target_operation_id`, `target_status`, and `cancelled`. `cancelled=true` means the target is confirmed cancelled, including cancellation before dispatch. A command that exits naturally keeps its actual success/failure and exit code; cancellation completes with `cancelled=false`. Cancelling an already terminal command is a recorded no-op with that final status. Cancellation never means rollback of filesystem writes or external effects.

Request acceptance, connection loss and a cancellation RPC acknowledgement do not imply that a process stopped. If execution evidence remains unknown, the target stays unknown and cancellation remains pending. Destroy stays independently available and does not manufacture a command result if the guest's final receipt was lost. Cancellation does not release allocation resources or retained command/output reservations. A confirmed guest cancellation queues output archival just like other confirmed terminal commands.

## Durable ownership

The [admission store](../crates/sandbox-store/src/cancel.rs) locks the target before the project, validates current credentials, resolves the project-wide retry key, then admits an operation of kind `cancel` with `target_operation_id` and phase `cancel_requested`. It rechecks credential expiry in the committing statement. The existing same-sandbox foreign key binds the target; [migration 0012](../migrations/0012_command_cancellation.sql) adds a unique index for unfinished requests in this phase. It changes no existing rows. Older generic cancellation records do not acquire authority through migration and are excluded from cancellation claims.

Each controller tick first reconciles at most one cancellation with a two-second overall database bound, then performs its usual host check, allocation maintenance and one create/execute/destroy action. A stalled cancellation transaction rolls back; any previously committed cancellation claim expires normally. This step does not require a healthy host and does not replace allocation maintenance. Accepted cancellation remains effective after the initiating token is revoked; new cancellation requests and public reads still require current authority.

Cancellation reconciliation locks its cancellation operation and original execute target. If the target is queued/running, has zero attempts and has no dispatch receipts, it can atomically mark the target cancelled and revoke an undispatched execution claim. Every execution dispatch action requires committed intent, so a delayed claimant cannot subsequently start it. The cancellation lease is checked before effects and in the final write; a lost lease rolls back both target and cancellation changes.

For a target with dispatch intent, only the original execution owner contacts the supervisor. [Execution preparation](../crates/sandbox-store/src/execute.rs) sees the pending cancellation and returns a cancellation action bound to the original operation, allocation, generation, producing host epoch and command digest. It never issues a second Execute or redirects work onto a replacement allocation. The independent cancellation operation only observes the target's eventual terminal status. Its claim grants no guest execution authority.

The [supervisor adapter](../crates/sandbox-supervisor/src/host/commands.rs) implements `CancelCommand` using the same bounded `CommandInspection` request, controller certificate pins, allocation gate and operation revision fences as inspection. Missing host dispatch history in the same epoch is durably fenced before returning `not_started`; a delayed Execute cannot defeat that fence. A dispatched command uses the bound guest client's idempotent cancellation call. Host-to-guest calls keep the three-second bound. Already final receipts are returned unchanged. Digest conflicts, stale revisions, wrong ownership and expired claims are rejected. No extra lifecycle revision slot is allocated for the separate cancellation operation.

Lost cancellation replies permit repeating cancellation under a new execution claim, never repeating execution. Missing guest receipts remain unknown. Old-epoch command ownership is still rejected. The separate [allocation recovery path](controller.md#previous-epoch-allocation-recovery) can verify cleanup after restart without inventing a command outcome. An old supervisor without the new RPC cannot confirm cancellation: the controller preserves uncertainty. Use matching component versions; host replacement and draining retain their existing lifecycle requirements.

## Validation

[PostgreSQL tests](../crates/sandbox-store/tests/support/cancel.rs) cover concurrent admission, pending conflicts, pre-dispatch cancellation, retained retry identity after compaction, accepted cancellation after credential revocation, unknown outcomes, terminal no-ops, cross-project targets, claim expiry during lock waits, abandoned admission and upgrades over generic cancellation rows.

[HTTP/controller tests](../crates/sandbox-controller/tests/cancel.rs) use real mTLS to the explicit fake. They cover running and queued cancellation, lost replies, delayed Execute fencing, natural completion, missing guest history, unchanged output/publication ownership, subsequent execution, destroy, body validation, expiry, stale ownership and cancellation during host health failure. The [controlled host tests](../crates/sandbox-supervisor/tests/host.rs) exercise actual process interruption and cleanup in a microVM, cancellation after a natural exit, and a no-start fence against a delayed Execute. These are admission/recovery checks and nested aarch64 development evidence; supported-host isolation and release gates remain separate.

[Recorded cancellation evidence](evidence/2026-09-21-aarch64-cancellation.json) pins matching Mac/Linux source hashes and actual guest, host, guardian, Firecracker, jailer and kernel artifacts. The final public API case confirms cancellation after observable process start, one execution marker, original retry identity, guest cleanup and subsequent database/VM resource release. The record distinguishes the final-source API run from the earlier eight host regressions and eleven guest-runner regressions, and lists setup corrections and scope limits.
